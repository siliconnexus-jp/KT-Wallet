# P1：广播缓存容量回归修复

状态：源码修复和本地测试完成，已按用户的测试环境授权部署提交 `632b93d`。未发送真实交易。本次不处理 P2 Android CI 初始化问题。

## 修复

- 在占用广播名额之前检查 EVM 交易封装：规范 RLP、完整长度、签名字段、legacy / type-1 / type-2 字段数量及 parity。深度与节点数有界。`0x0000` 等任意短十六进制不再进入 guard 或 RPC 上游。
- 4,096 现在是本地缓存容量，不再是使用 Redis 时的每日历史交易上限。已成功写入 Redis 的终态可以按 LRU 从本地移除；重放仍由 Redis 的原子 claim 和原结果约束。
- 没有 Redis 时，节点明确拒绝的结果允许在缓存满时淘汰；它没有产生已接受交易。已接受、状态未知和正在提交的本地记录不得以恢复吞吐为由移除。
- Map、过期堆和 LRU 一起删除，避免释放 map 后又留下无限增长的索引。清理仍有固定预算。
- 全部本地名额被不可淘汰记录占用时，仍允许读取其他实例已经保存在 Redis 的结果，不发起新的上游写入。
- Redis claim 失败发生在提交之前，不再遗留占用 24 小时的本地 pending。Redis 返回的其他实例 pending 也不再固定缓存 24 小时，后续能读到对方的完成结果。
- 已提交、但结果持久化失败的 accepted/unknown 保持本地保护，不作为可淘汰数据。
- 新增可选 `BROADCAST_REDIS_URL`，隔离读缓存与广播记录。启动时只读校验广播 Redis 为 `noeviction`；无法读取策略或仍用 `volatile-lru` 时拒绝启动，不擅自改 Redis 配置。

封装检查不是密码学验签，也不检查账户余额、nonce 或执行结果。节点仍是最终权威；即使数据封装正确、最终被节点拒绝，也不能再填满每日名额。格式依据：[EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)、[EIP-2930](https://eips.ethereum.org/EIPS/eip-2930)、[RLP](https://ethereum.org/developers/docs/data-structures-and-encoding/rlp/)。

## 验证

- 4,096 个畸形 ETH 请求：全部 InvalidParams、claim 数为 0；后续 Base 交易成功。
- 4,100 个封装完整但被节点拒绝的请求：有 Redis / 无 Redis 两种模式均不阻断后续 Base 交易。
- 4,100 个成功请求：本地淘汰旧记录后重放第一笔，上游总调用仍为 4,100，未重复广播。
- 超过 8,192 次容量与回放测试：本地 map、heap、LRU 始终有界。
- 覆盖不可淘汰记录、共享 pending 刷新、满缓存读取共享结果、提交前存储故障恢复、提交后持久化失败，以及并发完成/淘汰。
- `go test -race -count=1 ./...`、`go vet ./...` 通过。
- EVM 封装解析 10 秒 fuzz：247,770 次执行，无 panic。

## 运行边界

生产广播需继续使用可靠的 Redis，并保障其幂等数据的 24 小时保留与容量；不能将 Redis 的活动幂等 key 任意淘汰。无 Redis 的开发模式仍会在 4,096 条不可淘汰记录全部被占用时保守拒绝新提交，这是有限内存下保留防重复广播约束所需的边界，不是无限容量的生产替代方案。

旧实例是 `volatile-lru` 且 ACL 无配置读取权限，并通过 `rename-command CONFIG ""` 禁用了命令。部署时已调整为 `noeviction`，启用 CONFIG 并仅给广播用户只读 `+config|get` 权限。CONFIG SET 未授权，FLUSHALL / FLUSHDB 仍禁用。运行时修改策略、重启/清空丢失活动记录依然属于必须受控的运维风险。
